# Security design and self-assessment (seed)

Role E turns this into the *Security self-assessment report* deliverable. Every claim here points to a test you can run (`make test-security`).

## Threat model

| Asset | Threat | Primary control | Secondary control |
|---|---|---|---|
| Money in the sandbox wallet | The model (or injected text) moves money | Only T2 can execute, and only with a user-confirmed, signed, single-use, unexpired authorization whose terms are re-read from storage | Fixed tool registry; T3 names blocked; destination allowlist checked by the gate and again by the bank |
| Truthfulness of advice | The model invents or bends numbers | Deterministic verifier: every number must match a fact; warnings must be mentioned | Reply replaced by deterministic narration; `VERIFICATION_FAILED` audited |
| Suitability | Over-aggressive savings despite low capacity | Permitted profile = min(tolerance, capacity), recomputed server-side | Hard rules H1–H5 and U checks as tests (see "Suitability") |
| Integrity of evidence | Audit log edited after the fact | Hash chain (`prev_hash`, `event_hash`) | `GET /v1/audit/verify`; execution fails closed if audit writes fail |
| Authorization integrity | Stored terms edited after confirmation | HMAC-SHA256 with a server secret (not stored in the DB) | Exact canonical comparison of requested terms |
| Agent scope | Self-escalation (confirming for the user, granting itself permissions) | No confirm tool; the confirm endpoint requires the user actor | T3 audit events |
| Long-lived manipulation | Injected text persisted into memory | Typed user record; no free-text instructions stored (though valid record names can contain instruction-like letters) | Untrusted text wrapped as `{"untrusted_text": …}` |
| Identity | A caller claims another user (a forged `X-User-Id`, a guessed or stolen cookie, a replayed session) | Accounts mode (`NL_AUTH=accounts`, docker compose): the user id comes only from an `nl_session` cookie resolved server-side; `X-User-Id` is rejected (400) on every route but `GET /health`; only the token's sha256 is stored | Sessions expire 12 h after they open, never slide; sign-out revokes; the token and the email never reach a body, the audit, a log or an envelope |
| Cross-site requests | A foreign page makes the browser send the session cookie | Cookie `HttpOnly; SameSite=Strict; Path=/` (`Secure` over https); unsafe methods need an Origin in `NL_APP_ORIGINS` (a foreign or `null` Origin is 403), or, with no Origin, a JSON body | CORS never allows credentials; the UI calls the API on its own origin (`/api`) |
| Profile and tolerance | The model (or a replayed request) raises the declared tolerance or renames the user; a failed audit leaves an unrecorded change | Profile writes are user-only HTTP routes in accounts mode; the 4 profile-write tool names are T3 `SELF_ESCALATION`; personas are read-only | Each write commits with its `PROFILE_UPDATED` event or not at all, compare-and-set against the profile it read (a concurrent edit gets `INVALID_INPUT`, reload and retry) |
| Personal data in imported statements | Read by anyone who sets `X-User-Id` (demo mode), handed to the model by a tool, left in files or logs | Removed once at import, before anything is stored, by deterministic rules; only placeholders (`[PERSON]`, `[ID]`, …) and a masked account (`****3456`) remain (ADR-028) | An optional detector can only add masking; an import that cannot be redacted stores nothing; S15 checks every surface |
| Real data on a public sandbox | Sign-up is open (option B, ADR-038): a visitor stores a real bank statement or real personal data on a demo server | A sign-up notice that cannot be dismissed and a required acknowledgement, checked by the server (`sandbox_acknowledged`, recorded on `USER_REGISTERED`); the same warning above the statement upload | Everything personal is sealed at rest; the user can delete the account and all of its data (`DELETE /v1/account`) |
| Data at rest | A copy of the SQLite file, its WAL, a backup, or the whole Docker volume | Every personal payload sealed with AES-256-GCM, bound to table, owner and row; the email kept only as an HMAC blind index | The key is never in the database and, in a deployment, never on the data volume: a Docker secret, refused on the volume (`NL_DEPLOYMENT=deployed`) |
| Right to deletion | A user cannot remove their data; or a deletion breaks the audit chain for everyone | `DELETE /v1/account` with the password and a typed confirmation erases every row the user owns in one transaction and ends every session | The user's audit events become tombstones that a later `ACCOUNT_DELETED` event commits to, so the chain still verifies and a forged tombstone does not |

## Open sign-up and the sandbox notice (option B)

The public demo keeps sign-up open: anyone can create an account. `NL_DEMO_PERSONAS` only turns the shared Camila and Diego personas on or off; there is no setting that closes sign-up. The risk that remains is a visitor who stores a real cartola or real personal data on a server meant for synthetic data, which would make the operator responsible for personal data under Ley 21.719. Option B (ADR-038) keeps the door open and makes the rule explicit, then limits the damage:

- **Notice at sign-up.** The sign-up page always shows a notice that cannot be dismissed: this is a hackathon sandbox, and real bank statements or personal data must not be uploaded. The form has a required checkbox, and the server refuses a sign-up without it: `SignupRequest.sandbox_acknowledged` must be `true` (422 on that field otherwise, nothing stored). `USER_REGISTERED` records which notice was accepted (`sandbox_notice=sandbox-1`, `SANDBOX_NOTICE` in `application/use_cases/accounts.py`).
- **Email domain checks.** Sign-up refuses an email whose domain is a disposable inbox (the maintained `disposable-email-domains` blocklist, offline, parent domains included) or, with `dns`, a domain that does not exist or receives no mail (`email-validator`; a DNS timeout lets the email through). `NL_EMAIL_CHECKS` picks them; Docker runs both. No domain list lives in this repository. A refusal is 422 on `email` and stores nothing (`tests/adapters/test_email_domains.py`). It does not prove the user owns the address: there is no confirmation email.
- **Notice at upload.** The statement upload screen shows the same warning above the file picker, and the footer of every account page repeats it.
- **Damage control.** Whatever is stored anyway is sealed at rest (next section), and the user can delete it all (`DELETE /v1/account`, "Account deletion").

A notice is not a control: nothing can tell a real cartola from a synthetic one. See "Known risks".

## Data at rest and key management

**What is sealed.** The SQLite adapter (`adapters/outbound/persistence/sqlite.py`, `field_cipher.py`) seals every payload that holds personal or financial data with AES-256-GCM (12-byte random nonce, format `nlenc2:`). The associated data binds each value to its table, owner and row, so a value copied into another user's row or another table does not open.

| Table | Sealed column (associated data) | Clear columns (lookups and order) |
|---|---|---|
| `statements`, `transactions` | `payload` (`statements\|<user>\|<statement_id>`, `transactions\|<user>\|<txn_id>`): lines, descriptions, merchants, amounts, balances, obligations | ids, `user_id`, `posted_on` |
| `user_profiles` | `payload` (`user_profiles\|<user>\|<user>`): display name, language, declared tolerance, questionnaire answers | `user_id` |
| `user_accounts` | `payload` (`user_accounts\|<user>\|<user>`): email, scrypt password hash, creation time | `user_id`, `email_index` (HMAC), `sample_data` |
| `proposals`, `authorizations` | `payload`: terms, amounts, signature, snapshot, status | ids, `user_id`, `session_id`, `consumed_at` (authorizations) |
| `savings_rules` | `payload`: amount, frequency, accounts, start date | `rule_id`, `user_id` |
| `audit_events` | `record` (`audit_events\|<user>\|<event_id>`): the whole event, with `prev_hash` and `event_hash` | `sequence`, `event_id`, `user_id`, `session_id` |
| `sessions` | none: `session_ref`, `user_id`, `sha256(token)`, times | all (no personal content; the token itself is never stored) |
| `meta` | `key_check` (a known text sealed with the key) | `name` |

A value in clear is refused when read, so plain text cannot be slipped into a current database around the application. `PRAGMA secure_delete=ON` overwrites deleted rows. `tests/adapters/test_encryption_at_rest.py` writes an account, its questionnaire, a statement, a proposal, an authorization and a savings rule over HTTP, then reads the raw database and WAL bytes and finds none of the known values.

**Email.** The email is the account lookup, so it used to be a clear, unique column. It is now `email_index`: HMAC-SHA256 of the normalized address under a key derived for that purpose only. Sign-in and the sign-up duplicate check search that column; the address itself lives only inside the sealed account payload. Without the key, an index value cannot be tested against a guessed address. The enumeration guarantees (S20) are unchanged.

**Audit chain.** The hash is still computed over the plaintext record (`domain/audit/events.py`, unchanged), exactly what `neural-ledger export-audit` writes, so an export verifies without the key. At rest the whole record is sealed with its `prev_hash` and `event_hash` inside it: verifying needs the key, and the file shows no hash to test a guessed event against. `GET /v1/audit/verify` and `/health` open every record and verify the chain.

**Key hierarchy.** `NL_DATA_KEY` (32 random bytes, 64 hex characters) is never used directly. HKDF-SHA256 derives one subkey per purpose (`field_cipher.derive`):

| Subkey | HKDF `info` | Used for |
|---|---|---|
| field key | `neural-ledger/v2/field-encryption` | AES-256-GCM seal and open of every payload above |
| email index key | `neural-ledger/v1/blind-index/email` | HMAC-SHA256 of the normalized email (`email_index`) |

Values in the older `nlenc1:` format (sealed with `NL_DATA_KEY` itself, before option B) still open and are rewritten by the migration.

**Where the key comes from** (`bootstrap/data_key.py`). A key file first (`NL_DATA_KEY_FILE`, or the Docker secret `/run/secrets/nl_data_key` when it is mounted), then the `NL_DATA_KEY` environment variable. A deployment uses `docker-compose.data-key.yml`, which mounts the secret from `NL_DATA_KEY_SECRET_FILE` on the host and sets `NL_DEPLOYMENT=deployed`; `deploy/secrets/README.md` says how to generate it. In deployed mode the API refuses to start:

- without a key;
- with a key file on the same mount as the database (checked through `/proc/self/mountinfo`; without it, the database's directory counts);
- while the old offline key file `<NL_SQLITE_PATH>.key` still exists;
- with the development `NL_HMAC_SECRET`.

Live mode (any provider) needs a key as before. A local run without one keeps the convenient fallback, a random key in `<NL_SQLITE_PATH>.key`, and prints a loud warning that a copy of the volume reads everything; the base `docker-compose.yml` and CI stay on that path, so `docker compose up` still needs no key. Before using a key, the API opens the sealed key check in `meta` (or, in an older database, its first sealed value per column) and refuses a key that does not open it, before anything is written.

**Migration** (`neural-ledger migrate-data`, `bootstrap/migrate.py`, `adapters/outbound/persistence/sqlite_migration.py`). In one transaction: upgrade the schema (version 0 to 1: the email column becomes `email_index`; proposals, authorizations and audit events gain their `user_id`), open every sealed value with the new key or the old one (`<db>.key` or `--old-key-file`), seal it again with the new key, seal anything still in clear, write the key check; then VACUUM and a WAL checkpoint, so free pages keep no old copy. `--dry-run` reports and writes nothing; a second run changes nothing; a value that opens with no given key stops it with nothing written. It prints the command to delete the old key file. A database at schema 0 written with the current key (a local run) is upgraded the same way at startup. The same command rotates a key: point `--old-key-file` at the old key and the secret at the new one.

## Account deletion

`DELETE /v1/account` (accounts mode, signed in; rate limited at 5 per minute per caller and 10 per IP, since it checks a password) takes the password again and `confirm` = `DELETE` or the account's email (`contracts/auth/account_deletion_request.schema.json`). A wrong confirmation is 422 on `confirm`, a wrong password 401 `INVALID_CREDENTIALS`, and nothing is deleted. The profile page has a **Delete account** section: a button, then a form with the confirmation word and the password; the danger button stays disabled until both are filled.

In one transaction (`SqliteAccountErasure`, `InMemoryAccountErasure`) it deletes the user's statements, transactions, savings rules, proposals, authorizations, sessions, profile and account, then truncates the WAL. Every session of the account stops working because its row is gone, and the response clears the cookie. Conversations and snapshots, which live in memory, are dropped too. The response counts rows per table (`contracts/auth/account_deletion.schema.json`).

**The audit trail.** The chain is one log for every user, so removing A's events would break verification for everyone. Each of A's events becomes a **tombstone** instead: same `sequence`, `prev_hash` and `event_hash`, so the links still verify, and nothing else (kind `ERASED`, actor `system`, no user, session `erased`, the erasure's timestamp). A tombstone's content can no longer be re-hashed, so `verify_chain` accepts it only when a later `ACCOUNT_DELETED` event commits to it: that event has no user id and no session, and its detail holds the number of erased sequences, a sha256 of their list (`erased_events`, `erased_sha256`) and the row counts. Erasing another user's event, one event more, or editing the count fails verification. The tombstone choice keeps the evidence that something happened at that point without keeping what it was or who did it.

**Demo personas are reset, never deleted.** Camila and Diego are shared fixtures with no password. In a persona session the profile page offers **Reset demo data** instead: `confirm` = `RESET` deletes what visitors stored for the persona (statements, transactions, proposals, authorizations, savings rules) and tombstones its audit events under one `DEMO_DATA_RESET` event; the fixture and the visitors' sessions stay. Any visitor can reset a persona: it is a sandbox, and the reset is itself audited.

`tests/security/test_account_deletion.py` deletes user A and checks that user B is intact, that both of A's sessions end, that A can register again, and that no row of any SQLite table, sealed values included, refers to A's id, email, name or sessions.

## Permission tiers

| Tier | Capability | Control |
|---|---|---|
| T0 | Read financial state | Scoped to the user; audit reads return only the caller's events (`user_id` on every event), whatever session id is passed |
| T1 | Analyze and suggest | Facts and warnings on every output; stateful T1 (proposals) hidden in read-only turns |
| T2 | Execute an approved sandbox action | Signed terms, expiry (10 min), single use, exact match |
| T3 | New beneficiary, unknown destination, limit or credential change, policy override, self-escalation (including any profile or tolerance write: `update_user_profile`, `set_risk_tolerance`, `submit_questionnaire`, `update_profile`) | Always blocked and logged |

## Compliance map (laws and standards)

`backend/tests/security/test_compliance.py` turns each requirement below into a test that names its norm. A **C** row is a built control and its test passes. A **G** row is a duty that is not built yet: its test is a strict xfail marked `GAP`, so CI stays green and the gap stays visible, and the day the control lands the test XPASSes and the run fails until the marker is removed. A G row that is built moves to the built controls and keeps its ID. `test_every_compliance_test_is_in_the_security_map` fails if a C or G test is missing from this page. This is engineering evidence for counsel to review, not legal advice.

**Norms.** Ley 19.628 as amended by **Ley 21.719** (personal data; published 2024-12-13, **in force 2026-12-01**; article numbers per the [BCN summary of the law](https://obtienearchivo.bcn.cl/obtienearchivo?id=repositorio%2F10221%2F37137%2F1%2FInforme_12_25_Ley_Datos_Personales_rev.pdf)): art. 3 principles, arts. 5–9 rights, art. 12 consent, arts. 14 bis–14 sexies duties, art. 15 ter impact assessment, arts. 17–19 financial obligations data, art. 27 international transfers. **Ley 19.496** art. 3 b) (truthful, timely information). **Ley 21.663** (cybersecurity framework). **PCI DSS v4.0** (card data). **OWASP ASVS 5.0**, **OWASP API Security Top 10 (2023)**, **OWASP Top 10 for LLM Applications (2025)**.

**Existing attack tests and the norms they evidence:** S01, S13 → LLM01 prompt injection; S02, S03, S06, S13, S14 → LLM06 excessive agency; S04, S05, S11 → ASVS V2 business logic and V11 cryptography (HMAC, single use); S07, S08 → LLM09 misinformation and Ley 19.496 art. 3 b); S09 → suitability (hard rules H1–H5); S10 → fail closed (ASVS V16); S12 → ASVS V2 input validation; audit tests → Ley 21.719 art. 14 quinquies and ASVS V16.

### Obligations reviewed but not testable as code

- **Impact assessment (Ley 21.719 art. 15 ter).** Profiling a person's finances from bank statements is likely high-risk processing. Write the assessment before real users.
- **International transfers (art. 27).** Each provider below receives data only when its setting is on, and all are outside Chile. The LLM (`NL_LLM=openrouter`, or `anthropic` directly) receives the system prompt, the session's conversation history, the user's messages and tool results. Messages are free text cut at 4,000 characters and can contain identifiers the user types. Tool results hold financial figures, the profile's display name, pending actions and the session's audit events. No agent tool returns statements or transactions. Jev for decisions (`jev` in `NL_DECISION_CHAIN`) receives each chat message, to classify intent and detect injection, and the user's recent messages for the risk-tolerance question. Jev for categories (`jev` in `NL_CLASSIFIER`, ADR-032) receives each charge's statement-line text after redaction, never a deposit (`C13`). Azure AI Language (`NL_PII_DETECTOR=azure`) receives the raw text of each imported statement line, before redaction. All are off in offline mode. `C09` only guarantees that keys and the signing secret never reach the model, not that prompts are free of personal data. See [PRIVACY.md](PRIVACY.md) ("Who receives data") for the full table. Document the safeguards before live use with real users.
- **Financial obligations data (arts. 17–19).** The app does not communicate anyone's debts to third parties. Keep it that way, or review these articles first.
- **Ley 21.521 (Fintec) and the Open Finance System (CMF NCG 514).** Not applicable while statements are uploaded by the user. Connecting to banks through the system's APIs brings its consent and security rules, and its start date should be confirmed with the CMF.
- **Ley 21.663.** Its incident duties (an early alert within 3 hours to the national CSIRT) bind essential services and operators of vital importance. The app is neither, and the breach runbook (`docs/runbooks/INCIDENT_RESPONSE.md`) follows the same steps anyway.
- **Children's data (art. 16 quáter).** There is no age check. Personas and uploads are assumed to be adults.

## Suitability (hard rules H1–H5 and U checks)

`backend/tests/suitability/test_suitability.py` (`make test-suitability`) checks that savings and purchase advice fits the user's financial situation and declared tolerance, and that neither the user's nor the model's say-so can change that. H1–H5 are the Financial Core's hard rules (`docs/FINANCIAL_CORE.md` 4.8). The U checks cover the rest of the suitability process. Gaps (UG) are strict xfails, as in the compliance map. `test_every_suitability_test_is_in_the_results_table` fails if a test is missing from this page.

**Norms.** **Ley 19.496** art. 3 b) (truthful, timely information) is binding. The suitability benchmark is international good practice: **MiFID II** art. 25(2), **Delegated Regulation (EU) 2017/565** art. 54, and **ESMA's suitability guidelines** ([ESMA35-43-3172, 2022](https://prod.finanssivalvonta.fi/globalassets/en/publications/supervision-releases/2023/esma35-43-3172_guidelines_on_certain_aspects_of_the_mifid_ii_suitability_requirements.pdf)): GL1 informing the client, GL3 necessary information, GL4 reliable information without undue self-assessment, GL5 keeping it up to date, GL8 ability to bear losses, GL9 alternatives, GL12 records. In Chile, **Ley 21.521** (Fintec) regulates investment advice through CMF registration (NCG 502; NCG 503 accredits the advisor's own *idoneidad*). A savings and budgeting copilot is not investment advice today; review this if the product starts recommending financial instruments.

**Results** (`make test-suitability`, 2026-10-19, offline): 24 passed (the checks below, with UG02 and UG03 covered by several tests each, and the table check), 0 xfailed, 0 failed. The three gaps UG01–UG03 were closed on branch `c/suitability-gaps`.

## Known risks (residual)

- **Two identity modes** (`NL_AUTH`). `demo`, the code default for local runs, tests and the recorded demo, still identifies the user by the `X-User-Id` header: anyone who sets it can read anyone's statements and transactions (since ADR-028, financial data only: amounts, dates, merchants, categories and a masked account), so demo mode must never be exposed publicly; it has no profile writes and no auth routes. `accounts`, set in docker compose, uses sign-up/sign-in with cookie sessions. Running locally with the defaults therefore differs from the deployed API; test the deployed path with `NL_AUTH=accounts`.
- **G01 depends on the mode; it is not fixed globally.** In `NL_AUTH=demo` the gap is still open: identity is the header, and a request without credentials is served. In `NL_AUTH=accounts` it is mitigated: the user id comes only from the `nl_session` cookie resolved server-side, and `IdentityGuard` rejects `X-User-Id` (400) and requests without a session (401). The G01 test runs against the default (demo) app, so its strict xfail stays until demo mode is covered too.
- **Sign-up is open (option B, ADR-038).** Anyone can create an account, there is no setting that closes sign-up, and email ownership is not verified. The sandbox notice and its acknowledgement make the rule explicit and are recorded, but they are not a control: nothing tells a real cartola from a synthetic one, and a visitor can still store real data. Everything stored is sealed at rest and deletable by its owner; an operator who finds real data deletes it through the incident runbook. Open sign-up also allows abuse (mass sign-ups, storage use); the per-IP limits (G07) and the edge rate limit are the only brakes.
- **Demo personas are shared.** A demo session opens `camila` or `diego` for any visitor (`NL_DEMO_PERSONAS=false` turns it off). Visitors share that persona's statements, chat history and audit trail; the persona's profile is read-only, but an uploaded statement is visible to the next visitor of the same persona, until any visitor resets it (`DEMO_DATA_RESET`). A real statement uploaded under a persona is exposed to every other visitor, which is worse than in an own account: the upload warning applies there too.
- **Sign-in has a per-IP rate limit but no lockout** (G07; D10 cut the lockout). `POST /v1/auth/` allows 10 attempts per minute per IP, and scrypt runs on every attempt, so brute force is slow but not stopped; an attacker spread over many IPs is not limited per account. Sign-up answers 409 for a registered email, which reveals that it exists (sign-in does not).
- **Email ownership is not verified, and there is no password or account recovery.** A forgotten password also means the account cannot be deleted by its owner (deletion asks for it); the operator can delete it by hand.
- **Profile names reach the model.** `display_name` is wrapped as untrusted text, but the wrapper is a soft layer: instruction-like names made only of letters can pass syntax validation. Domain policy remains the authority for decisions.
- **New accounts have no inferred financial model.** Imported statements are not ingested as statement-to-forecast data, so empty or sample future features do not represent real-user projections.
- **The Origin check trusts the listed origins.** `NL_APP_ORIGINS` must name the exact public UI origin (no `*`, no `null`); a request without an Origin is accepted only with a JSON body, which a cross-site HTML form cannot send. `SameSite=Strict` is the other half of the defence.
- **`X-Forwarded-Proto` decides `Secure` when `NL_COOKIE_SECURE=auto`.** A client can only make the flag stricter by sending it; behind a TLS proxy set `NL_COOKIE_SECURE=true`.
- **Sessions are not bound to a device**: a stolen cookie works until it expires (12 h) or the user signs out.
- **The identity guard also covers `/docs`, `/openapi.json` and any future route** in accounts mode; `tests/http/test_auth_api.py` walks every route so a new one cannot be public by accident.
- **What encryption at rest does not hide** (G11). Ids, user ids, session ids, the token digest, transaction posting dates, audit sequence numbers, `consumed_at` and `revoked_at` stay in clear: a copy of the file shows how many users, statements, transactions and events there are and when transactions were posted, but no content. Statement import events log under the shared session id `statements`. The key protects a copy of the file, the volume or a backup; it does not protect against someone who controls the running host (root can read the mounted secret and the process memory) or against the application itself.
- **Key management is manual.** The key is a Docker secret file on the host (`NL_DATA_KEY_SECRET_FILE`), readable by the container user, with no KMS, no HSM and no automatic rotation; rotating means running `migrate-data` with the old key as `--old-key-file`. Losing the key loses every account, profile and statement, so it is backed up apart from the database backups. A local run without a key still keeps it next to the database (with a warning); that is never a deployment.
- **Tombstones keep a trace.** After a deletion the chain keeps, for each erased event, its position, its event id and its original hash, and the `ACCOUNT_DELETED` event keeps row counts. None of it names the user, but the number of events and the time of the deletion remain. The hash is over the plaintext record, sealed at rest; an export written before the deletion still holds the full events and is not reached by it.
- **The host is outside the scope of option B.** This change hardens the application and its Docker setup only. The server (its operating system, SSH access, Docker daemon, backups, the Cloudflare Tunnel token) is not covered: SSH hardening on the server is pending, and anyone with root on the host can read the data key and the database. The deployment override and runbook live on `ops/deploy-neural-ledger`, which is not merged.
- **Rate limits are per process and per IP as uvicorn sees it** (G07). Counters live in memory: a restart resets them and each worker counts on its own. In demo mode the caller is the `X-User-Id` header, which a client can rotate, so the per-IP budget is the one that holds. Behind nginx the IP comes from `X-Forwarded-For`, trusted only from private ranges (`FORWARDED_ALLOW_IPS` in docker compose); port 8000 is published for development and a caller on it can set that header, so a deployment should publish only the web port. Several users behind one NAT share the per-IP budget.
- **The redaction rules are written for Chilean cartolas.** They catch RUTs, long numbers, emails, phones and the counterparty of a transfer; a name elsewhere (`PAGO A <name>`) stays unless a detector is on. Rules are checked against real cartolas only locally (`cartolas/`, never committed, counts shared). Statements stored before `st-0.2` keep their raw text: delete the local database and import again (ADR-028).
- **Jev categorization is off by default** (`NL_CLASSIFIER=naive_bayes`). With `NL_CLASSIFIER=jev,naive_bayes` (ADR-032) the text of each charge, after redaction, goes to Jev through OpenRouter (or TypeSafe): a transfer to providers abroad under Ley 21.719, limited to placeholders and merchant names (C13). A name the rules miss (see below) would leave with it. Jev only picks a label from the vocabulary; it never sees a deposit and cannot change an amount, a kind or a permission (S22). `/health` shows the chain (`classifier`).
- **Azure AI Language is off by default** (`NL_PII_DETECTOR=none`) and is never the only layer. Turning it on (`NL_PII_DETECTOR=azure` with `AZURE_LANGUAGE_ENDPOINT` and `AZURE_LANGUAGE_API_KEY`) sends the raw text of every imported statement line to Microsoft. Detection is synchronous and stateless (REST API 2026-05-01), and `loggingOptOut` is sent as true. It needs the team's agreement on the subscription and the key, billing is per 1,000 characters, and `/health` shows it (`pii_detector`). Docker, CI and the recorded demo run with the rules only, and CI checks that.
- **`transfer_own` is trusted by the estimators** (ADR-012). A real outflow mislabelled as an own transfer would vanish from variable spend and overstate the protected surplus. The synthetic ledgers reconcile per account; real data would need two-leg matching of own transfers.
- **Read-only connections are read-only on our side only** (ADR-047). A connected MCP server can lie about what a tool does: we never call a tool that declares itself writing or destructive, has a write verb in its name or needs arguments, and only the user's sync calls one, with empty arguments; but a server whose `get_portfolio` moves money would still be called. Connect only servers you trust. The address is checked (https, public addresses only, no redirects) but resolved again when the request is sent, so a DNS answer that changes in between (DNS rebinding) is not caught; live connectors are therefore off on a public deployment unless `NL_CONNECTORS_LIVE=true`. What a service returns is redacted by the rules before it is stored, wrapped as untrusted text for the model, and never used in the forecast. Fintoc's link token is sealed at rest; whoever holds it and the secret key can read that bank account's movements.
- **The rules decision model is keyword-based.** It is the offline floor, not the main defence. The hard guarantees come from the gate and the confirmation contract, which do not depend on any model.
- **The verifier checks numbers, warnings and a few phrases.** Semantic contradictions in free prose need the model-based check (Should).
- **No abuse detection** on the API beyond the G07 rate limits.
- **The secret comes from the environment** (`NL_HMAC_SECRET`); a KMS is out of scope. Live mode refuses the development default (G10); offline mode accepts it, so never use it in a recorded demo.
- **Real statements are processed locally.** A developer's own cartolas in the git-ignored `cartolas/` are read on their machine; the repository and the test suite hold synthetic data only (C01, C02, C07). The repository is public: never commit keys or personal documents.
- **Estimator warnings are not forwarded.** `LedgerModelSource.load` discards the stage-1 `Envelope` warnings and facts, and estimation caveats have empty `must_mention`. Chat verification cannot enforce caveats it never receives; B must decide forwarding semantics before the ledger-default switch. See `docs/EXPLANATION_HANDOFF.md`.
- **The rolling-origin backtest is synthetic-only implementation validation.** Grid A December coverage is adverse without a prior December; this is not evidence of real-world predictive accuracy or a security mitigation. See `docs/BACKTEST.md`.
