\section{Executive summary}\label{sec:summary}

Neural Ledger is a cash-flow copilot that reads bank statements, forecasts a user's liquidity and can create a savings
rule in a \emph{sandbox} bank. Its core security property is that no language model can move money or set a number:
amounts are computed by deterministic code, actions need a signed authorization that only the user can create, and every
reply is checked against the facts the tools returned. That property is covered by attack tests S01--S24,
S30--S32 and S35--S38, and by the memory tests, and was not changed by this assessment.

This assessment was triggered by a review of the public demo. Anyone can sign up there, so a visitor could store a real
bank statement on a server that is meant for synthetic data. Personal data at rest was only partly encrypted, and the
encryption key sat on the same volume as the database. The team chose \emph{option B}: keep sign-up open, harden the
application and say so (ADR-038). After option B:

\begin{itemize}
  \item sign-up shows a sandbox notice that cannot be dismissed, with an acknowledgement the server enforces and records;
  \item every personal payload in the database is sealed with AES-256-GCM, and the email is found through a keyed HMAC index;
  \item in deployed mode the key comes from a Docker secret, and the API refuses to start if the key is on the data volume;
  \item users can delete their account and all of its data, and the shared audit chain still verifies afterwards.
\end{itemize}

The largest residual risks (\cref{sec:residual}) are four. A notice cannot stop a visitor from uploading real data (R01,
R02). Anyone with root on the host can read both the key and the data (R03). Until the server is migrated, the demo
still runs the old configuration (R24). Finally, consent and opposition are not built (R23).

\textbf{Version 1.1} reviewed four features merged since (ADR-039, ADR-040, ADR-044, ADR-047). They bring new
third-party text, a provider token with full access, and outbound calls to addresses users choose. The agent stays
read-only towards all of them, and every new store is sealed and erased with the account. The new risks were R25--R31.
The largest is that a connected server may lie about a tool being read-only (R25).

\textbf{Version 1.2} reviews what \code{main} gained after that: the fixes of pull request \#58, which now count live
connectors as live mode (R28) and give connection calls their own rate budget (R29); a download of the user's own
data (G02, closed); and typed user memory, saved only (ADR-048). Memory adds a place where text the user types becomes
stored state, and the answer is that nothing the model says can write it: the two memory tools take no arguments, the
user confirms every declaration, and a per-user fence stops a reply from outliving a revoked consent. The new risks are
R32--R35. None is rated above medium likelihood, and the largest impact belongs to the download, which anyone holding a
stolen session cookie could use (R35).

\subsection{Transport}

TLS ends at Cloudflare's edge. The deployment override on \code{ops/deploy-neural-ledger} publishes no host port, so
the API can be reached only through the tunnel. Its nginx configuration redirects plain HTTP to HTTPS and adds HSTS,
\code{X-Frame-Options: DENY}, a referrer policy and a strict content security policy. The API itself adds
\code{nosniff} and \code{no-store} to every response (G09). Behind the tunnel, nginx and the API talk plain HTTP on the
Compose network, and the API trusts \code{X-Forwarded-For} only from private ranges. The base \code{docker-compose.yml}
publishes port 8000 for development, so a deployment must use the override.

\subsection{Application and authentication}

\begin{itemize}
  \item \textbf{Identity} (accounts mode, \code{adapters/inbound/http/identity.py}): the user id comes only from a session
    cookie resolved on the server. \code{X-User-Id} is answered with 400. An unsafe request needs an allowed Origin, or a
    JSON body when there is no Origin. Every non-public route needs a session; a route-inventory test
    (\code{tests/http/test_auth_api.py}) fails if a new route is public by accident (S16).
  \item \textbf{Sessions}: twelve hours from creation, no sliding, revoked at sign-out. Only the token's SHA-256 is
    stored (S17).
  \item \textbf{Passwords}: scrypt with $N = 2^{14}$, $r = 8$, $p = 1$. Sign-in costs the same and answers the same
    whether or not the email exists (S20); sign-up reveals a registered email with 409.
  \item \textbf{Rate limits} (G07): per caller and per IP, one-minute windows. Ten sign-in or sign-up attempts per IP,
    five account deletions per caller, ten uploads per caller, and ten per caller on investment syncs and on each connection call.
    Counters live in memory, per process.
  \item \textbf{Input}: uploads are typed by their bytes and capped at 15\,MB (C05); hand-parsed JSON bodies are capped at
    16\,KiB; SQL is always parameterized, and a static test checks every SQLite module (C08).
  \item \textbf{Agent}: four permission tiers and a deterministic gate; signed, single-use authorizations only the user
    can create; terms re-read from storage; a verifier that rejects unsupported numbers and missing warnings
    (S01--S14, S19, S22, S23). Receipts, concept cards, Fintual goal names and connected services' answers reach the
    model only as untrusted text, and no tool stores, links or syncs anything (S24, S30--S32, S36). The memory tools take no arguments and refuse any;
    twelve tool names that would write memory are T3.
  \item \textbf{Outbound calls}: a connected server's address must be HTTPS and resolve only to public addresses;
    redirects are never followed; answers are capped at 1\,MB after 10\,s. A tool is enabled only if it is read-only,
    not destructive, takes no arguments and has no write verb in its name (S35, S37).
  \item \textbf{Email domains}: sign-up refuses disposable-inbox domains and, with \code{dns}, domains that receive no
    mail.
  \item \textbf{Sandbox notice}: sign-up requires \code{sandbox_acknowledged = true}, and \code{USER_REGISTERED} records
    \code{sandbox_notice=sandbox-1}. The upload screen warns again.
\end{itemize}

\subsection{Key management}

\begin{figure}[htbp]
  \centering
  \input{common/figures/keys}
  \caption{Key hierarchy. Each purpose has its own subkey derived with HKDF-SHA256; the HMAC secret for authorizations
  is a separate root.}\label{fig:keys}

The data key is read from \code{NL_DATA_KEY_FILE} or the Docker secret \code{/run/secrets/nl_data_key}, then from
\code{NL_DATA_KEY} (\code{bootstrap/data_key.py}, \cref{fig:keys}). With \code{NL_DEPLOYMENT=deployed} the API refuses
to start in four cases, checked before it opens the database:
\begin{itemize}
  \item there is no key;
  \item the key file shares the database's mount (read from \code{/proc/self/mountinfo}) or its directory;
  \item the old \code{<db>.key} still exists;
  \item the HMAC secret is the development default.
\end{itemize}
A sealed key check in the \code{meta} table rejects a wrong key before anything is written.
\code{neural-ledger migrate-data} re-seals every value in one transaction, with a dry run, and is idempotent; the same
command rotates keys. Local runs keep a key file next to the database and print a warning.
\code{tests/adapters/test_data_key.py} covers each refusal, the wrong key, the dry run, idempotence, and a migration
stopped by a value that opens with no given key.

\subsection{Host}

The host is out of scope. Root on the host can read the mounted secret, the volume and the API's memory; so can anyone
who controls the Docker daemon. SSH hardening on the server is pending. Backups of the volume must never contain the
secret file, and the key needs a backup of its own, outside the database backups.

\section{Account deletion and the audit trail}\label{sec:deletion}

The audit trail is evidence, so it must resist editing. It is also personal data, so a user must be able to have it
erased (Ley 21.719 art.~7). Option B reconciles the two with tombstones. When an account is deleted, each of its audit
events keeps its place in the chain (sequence, \code{prev_hash}, \code{event_hash}) and loses everything else. One
\code{ACCOUNT_DELETED} event, with no user id, commits to the exact list of erased sequences. \code{verify_chain}
accepts a tombstone only under such a commitment (\cref{fig:chain}). The deletion itself is one transaction
(\cref{fig:deletion}).

\begin{figure}[htbp]
  \centering
  \input{common/figures/deletion}
  \caption{Account deletion: password and confirmation, one transaction, tombstones, a committing erasure event.}\label{fig:deletion}
\end{figure}

\begin{figure}[htbp]
  \centering
  \input{common/figures/chain}
  \caption{The chain after an erasure.}\label{fig:chain}
\end{figure}

Evidence (\code{tests/security/test_account_deletion.py}, run on the memory and SQLite adapters):
\begin{itemize}
  \item A wrong password or confirmation deletes nothing.
  \item Deleting user A ends both of A's sessions and leaves user B's statements, transactions, profile, rules and
    sign-in intact.
  \item No row of any SQLite table refers to A's id, email, name or sessions, including the contents of opened sealed
    values; A's id is not in the raw file at all.
  \item A can register again with the same email.
  \item Forged tombstones fail verification: erasing B's event, a tombstone without an erasure event, an edited count,
    and a tombstone after its erasure event.
\end{itemize}
Demo personas are reset, not deleted, and the reset is recorded as \code{DEMO_DATA_RESET}.

\section{Known-risk register}\label{sec:register}

\lvl{Low} means it needs an unusual mistake or a privileged attacker. \lvl{High} impact means real personal data exposed
or lost, or the security model broken; \lvl{Low} means limited to metadata, availability of the demo, or the sandbox.
Owners are the team's roles (A finance, B agent, C platform, D frontend, E quality) or \emph{Ops}, the people who run the
server. The register is our own analysis of the code and of the option B change.

\section{Residual risk after option B}\label{sec:residual}

\begin{figure}[htbp]

Option B moves three risks down. A copy of the database or of the volume no longer reveals content; before, the email,
profiles, proposals, rules and the audit chain were plain text, and the key sat next to the data. A user can now remove
their data. And the sandbox rule is explicit and recorded. What remains, in order of priority:

\begin{enumerate}
  \item \textbf{Complete the redeploy} (R24, R06): migrate the server with the rehearsed steps, delete the old key file
    and the pre-migration backup, and merge the deployment branch so that the repository describes what runs.
  \item \textbf{Real data despite the notice} (R01, R02). This is the risk option B accepts. Refusing statement uploads in
    persona sessions would remove R02 at little cost. Option A (closing sign-up, or Cloudflare Access) remains available
    if real data is ever found.
  \item \textbf{The host} (R03, R05). Harden SSH, restrict who controls Docker, and keep the key and its backup out of the
    database backups.
  \item \textbf{Authentication depth} (R09, R10, R12). Add a per-account lockout or a delay, email verification, and an
    abuse budget for sign-up.
  \item \textbf{Compliance} (R23, R16). Export is built (G02). Build consent and opposition, write the impact
    assessment, and document transfer safeguards before any use with real users.
  \item \textbf{Connections} (R25, R26). Pull request \#58 closed R28 and R29. Pin the address that was checked, and
    keep live connectors off the public demo.
  \item \textbf{Memory and the export} (R33, R34, R35). Roles A, C and E sign ADR-048 and ADR-049 or switch the routes
    off before real users; bump the schema version when the next table is added; and ask for the password before the
    copy is downloaded. If the gate on 22 October 2026 lets a declared salary change the forecast, the assessment of
    memory must be redone, because that is the point at which words become numbers.
\end{enumerate}

\section{Conclusion}

For a hackathon sandbox, the application's controls are proportionate. Its core claim, that a model cannot move money
or invent a number, is tested against a hostile model. After option B, personal data at rest is sealed with a key kept
apart from the data, and it can be erased without breaking the evidence trail. The remaining exposure is mostly
organizational: what visitors choose to upload, how the server is operated, and the legal duties that a production
service would still have to meet.
