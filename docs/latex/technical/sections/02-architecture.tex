\section{System architecture}\label{sec:architecture}

\subsection{Layers and the dependency rule}\label{sec:layers}

The backend is a clean (hexagonal) architecture in four packages (\cref{fig:architecture}). The rule is one-way:
\code{adapters} depend on \code{application}, which depends on \code{domain}; \code{bootstrap} wires concrete adapters
into use cases and nothing imports it. \code{domain} and \code{application} import only the Python standard library:
no FastAPI, no SDK, no clock, no randomness, no file or network access. \code{tests/architecture/test_dependency_rule.py}
parses every module's imports and fails the build on any violation; FastAPI may appear only in
\code{adapters/inbound/http}.

  layers. Solid arrows inside the api are the dependency rule; dotted arrows are wiring by \texttt{bootstrap}. In a
  deployment the data key arrives as a Docker secret, separate from the data volume.}\label{fig:architecture}
\end{figure}

offline, so swapping a provider means one adapter file and one registry entry in \code{bootstrap/container.py}
(\cref{tab:ports}).

Four more settings choose a feature's adapters, and each defaults to one that needs no network.
\code{NL_INVESTMENTS} is \code{fixture} or \code{fintual}; deployed mode refuses \code{fintual}.
\code{NL_CONNECTORS} is \code{fixture} or \code{live}; in deployed mode, live connectors are off unless
\code{NL_CONNECTORS_LIVE} is true, and \code{NL_MCP_ALLOW_PRIVATE} (http and localhost servers) is refused.
\code{NL_KNOWLEDGE_BASE} is \code{lexical}, or \code{chroma,lexical} for a fallback chain. \code{NL_EMAIL_CHECKS} is
\code{disposable} and optionally \code{dns}.

\code{docker-compose.yml} is the submission and CI path: it runs offline, in accounts mode, with SQLite on the
\code{ledger-data} volume, and needs no key; without one the API creates a key file next to the database and prints a
warning. It also turns on both email checks. The compose profile \code{rag} adds a \code{chroma} container
(\code{chromadb/chroma:1.5.9}, volume \code{chroma-data}, no published port) that the API reaches through
\code{NL_KB_URL}. The API still embeds the questions; if the container is down, the lexical index answers. A deployment adds \code{docker-compose.data-key.yml}, which mounts the data key as a Docker secret at
\code{/run/secrets/nl_data_key} and sets \code{NL_DEPLOYMENT=deployed}. The public demo's own override (no host ports,
Cloudflare Tunnel, security headers in nginx) lives in \code{deploy/docker-compose.deploy.yml} on the branch
\code{ops/deploy-neural-ledger}, which is not merged at the commit described here.

\subsection{HTTP surface and identity}\label{sec:http}

\code{adapters/inbound/http/app.py} is thin: parse the request, call one use case, serialize with \code{to_primitive}.
In accounts mode the pure ASGI middleware \code{IdentityGuard} (\code{identity.py}) runs before any route and before any
body is read, in this order:
\begin{enumerate}
  \item any \code{X-User-Id} header, on any route but \code{GET /health}, is answered \code{400 IDENTITY_HEADER_REJECTED};
  \item an unsafe method (POST, PUT, PATCH, DELETE) needs an \code{Origin} listed in \code{NL_APP_ORIGINS} or, without an
    Origin, a JSON body, which a cross-site HTML form cannot send (\code{403 ORIGIN_REJECTED});
  \item every route outside \code{PUBLIC_ROUTES} (health, chain verification, sign-up, sign-in, demo session) needs a
    valid \code{nl_session} cookie (\code{401 UNAUTHENTICATED}); the resolved \code{Session} is the only source of the
    user id.
\end{enumerate}
Sessions last twelve hours from creation and never slide; the cookie is \code{HttpOnly}, \code{SameSite=Strict},
\code{Path=/}, and \code{Secure} over HTTPS. Only the SHA-256 digest of the token is stored. Outside the guard,
\code{RateLimitMiddleware} counts per caller and per client IP in one-minute windows; \code{SecurityHeadersMiddleware}
adds \code{X-Content-Type-Options: nosniff} and \code{Cache-Control: no-store} to every response.

\subsection{A chat turn}\label{sec:chat}

The application, not the language model, owns the flow of a turn (ADR-003, \code{application/use_cases/chat.py},
\cref{fig:chat}). The message is cut at 4{,}000 characters. A decision model (the rules, or Jev first and the rules
behind it) classifies the raw text, independently of the language model, into an intent with a confidence and an
injection flag. A deterministic gate (\code{domain/agent/policy.py}, policy \code{ap-0.2}) then decides: suspected
injection is refused; a confident (at least 0.80) out-of-scope intent is refused; a confidence between 0.55 and 0.80
gets a clarifying question and no tool; below 0.55, or when no decision model answered, the turn is read-only (tiers T0
and T1, without the stateful proposal tools); at 0.80 or above, tiers up to T2 are allowed. The language model chooses
among the tools of the allowed tiers, up to eight rounds. Its reply is checked by the
verifier; an honest mistake (an unsupported number or a missing warning) may be repaired once, and anything else is
replaced by a deterministic narration built from the facts. Every step is audited.

\begin{figure}[htbp]
  \centering
  \input{common/figures/chat}
  \caption{One chat turn. Shaded steps are deterministic code; the language model only selects tools and writes prose.}\label{fig:chat}
\end{figure}

The tool catalog (\code{application/catalog.py}) is fixed; its tiers must match the \code{x-tier} annotation of each
contract in \code{contracts/tools}, which a contract test checks (\cref{tab:tools}). Tool names that would grant a
capability the agent must never have (add a beneficiary, transfer funds, change limits or credentials, override the
policy, confirm an action, write the profile or the tolerance, and save, confirm, edit or delete memory or its consent) are recognized and blocked as tier T3 with a reason
(\code{PROHIBITED_CAPABILITIES} in \code{domain/permissions/policy.py}).

\subsection{The confirmation contract}\label{sec:confirmation}

Money can move (in the sandbox) only through three steps, each audited (\cref{fig:confirmation},
\code{application/use_cases/actions.py}). \emph{Propose} creates a pending proposal valid for 30 minutes. A savings
rule's amount comes from a stored plan snapshot, never from model text; a liquidity floor's amount is accepted only if
the user wrote that number in the same turn (ADR-037). A stored plan records the origin of the state it was sized
on. If a new statement, a new as-of date or a new floor has changed that state, proposing or confirming the plan is
blocked with \code{PLAN_SUPERSEDED} (UG02). \emph{Confirm} is reachable only from the UI endpoint
\code{POST /v1/actions/proposals/\{id\}/confirm} with the user as actor; the terms shown must equal the proposal's
canonical terms. It creates an authorization whose \code{action_hash} is HMAC-SHA256 of the canonical terms under
\code{NL_HMAC_SECRET}, valid for ten minutes. \emph{Execute} re-reads the terms from that authorization, passes the
gate in \cref{alg:gate}, writes \code{EXECUTION_STARTED} (if the audit cannot be written, nothing executes), consumes
the authorization atomically, and only then calls the sandbox bank.

The same rule, that the agent proposes and only the user writes, covers the newer features through user-only HTTP
routes, none of them a tool. An expense said in chat is prepared by \code{propose_expense} and stored only when the
user confirms it in a card (\code{POST /v1/expenses/\{id\}/confirm}). A receipt is corrected in a form
(\code{PATCH /v1/receipts/\{id\}}). An investment account is linked, synced and unlinked under \code{/v1/investments},
and a connection is added, has its tools enabled, is synced and is removed under \code{/v1/connections}. Tool names
that would link or unlink an investment account are T3 \code{CREDENTIAL_CHANGE}. The salary a user declares follows the
same rule: \code{propose_income_change} reads the amounts from the message that started the turn and prepares a card,
and only the user confirms it (\code{POST /v1/memory/proposals/\{id\}/confirm}) or declares it in the profile
(\code{PUT /v1/profile/income}); twelve tool names that would write memory are T3 \code{SELF_ESCALATION}
(\cref{sec:memory}).

\begin{algorithm}[htbp]
  \caption{Execution gate (\texttt{check\_execution}, \texttt{domain/permissions/policy.py}).}\label{alg:gate}
  \KwIn{authorization $a$ (or none), caller $u$, requested terms $q$ (optional), time $t$, policy $P$, signature check $s$}
  \KwOut{allowed, or blocked with a reason}
  \lIf{$a$ is none}{\Return blocked \code{AUTHORIZATION_NOT_FOUND}}
  \lIf{$a.\mathit{user} \neq u$}{\Return blocked \code{WRONG_OWNER}}
  \lIf{$t \geq a.\mathit{expires}$}{\Return blocked \code{AUTHORIZATION_EXPIRED}}
  \lIf{$a$ was consumed}{\Return blocked \code{AUTHORIZATION_REPLAYED}}
  \lIf{not $s$, i.e.\ HMAC of $a.\mathit{terms}$ $\neq a.\mathit{action\_hash}$}{\Return blocked \code{AUTHORIZATION_TAMPERED}}
  \lIf{$q$ given and canonical($q$) $\neq$ canonical($a.\mathit{terms}$)}{\Return blocked \code{AUTHORIZATION_MISMATCH}}
  \lIf{action, source or destination not allowed, or (action, source, destination) not a route of $P$}{\Return blocked (T3)}
  \lIf{amount $>$ the action's limit (1{,}000{,}000 per transfer; 100{,}000{,}000 for a floor)}{\Return blocked \code{AMOUNT_OVER_LIMIT}}
  \Return allowed (T2)\;
\end{algorithm}
